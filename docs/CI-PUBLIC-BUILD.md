# Building the firmware yourself, in GitHub Actions

`.github/workflows/public-build.yml` builds a Reaper firmware image from source
in a clean room, from public inputs only. You can run it in your own fork — you
do not need access to this repository, a Broadcom SDK, or a local Linux box.

It is the same build the maintainer runs locally. The workflow does not
reimplement anything: it recreates the documented build environment and then
calls this repo's own build engine (`build-scripts/_reaper_build_lib.sh`), the
same file that produces the published releases, and runs the same
`reaper_verify.sh` QA gate.

---

## Run it

1. **Fork** this repository.
2. In your fork, open **Actions**. GitHub disables workflows on new forks — click
   the button to enable them.
3. Select **Build firmware from source** → **Run workflow**.
4. Choose a variant:
   - `MCP` — the standard image (includes the read-only Advisor MCP server).
   - `noMCP` — the same firmware with the MCP server compiled out.
   - `both` — builds each in its own job, in parallel.
5. When the run finishes, download the artifacts from the run summary page.

It runs on free GitHub-hosted runners and uses your fork's Actions minutes.

---

## What you get

| Artifact | Contents |
|---|---|
| `firmware-RT-BE96U-<variant>` | the flashable `.pkgtb` image |
| `evidence-RT-BE96U-<variant>` | full build log, provenance record, SHA-256 sums, staged-filesystem digest |

The recovery `_loader.pkgtb` is deliberately not produced as an artifact; it is
not part of a normal upgrade and is not distributed.

---

## What the run proves

**1. The source is the published source.** After applying the patch series, the
workflow computes the Git tree hash of `release/src/router` and checks it against
`provenance/manifest.json`. When the manifest has an entry for that patch count,
a mismatch **fails the build** — the tree hash is timestamp-free, so this is an
exact proof that the source being compiled is the source the published firmware
came from. When there is no recorded entry yet, the computed hash is printed as
a warning so it can be recorded.

**2. The image passes the project's QA gate.** `reaper_verify.sh` runs after the
compile and blocks on failure: ARM ELF checks on core binaries, `httpd` and
`smbd` shared-library link closure, Samba flag/binary consistency, MCP-vs-noMCP
purity, critical page presence, i18n dictionary lockstep and quote safety, FIT
model identity read out of the packed image, per-model banner SHA-256, and the
rung-critical patch markers in `build-scripts/verify_markers.txt`.

**3. Whether it reproduces the published release.** The run compares its image
SHA-256 against the published `SHA256SUMS` carried in `releases/`. Read that
result carefully:

- A **`.pkgtb` hash mismatch is expected and is not a defect.** SquashFS embeds
  build timestamps, so two builds of identical source produce different image
  hashes.
- The meaningful comparison is the **staged-filesystem digest**, printed in the
  provenance record and backed by the `stagedfs-*` files in the evidence
  artifact. It hashes the staged rootfs — every path, mode, symlink target and
  file content — and is free of timestamps. Two builds of the same source should
  produce the same staged-fs digest. Comparing a CI digest against a local
  build's digest is the real reproducibility test.

## Why only RT-BE96U

The published `patches/` series reproduces one branch: `be96u-only`, the RT-BE96U
canon. The other four models (RT-BE86U, RT-BE88U, GT-BE98, GT-BE98_PRO) are
separate branches generated by `build-scripts/port_sibling_v2.sh`, which needs a
clone holding all five branches so it can compute the shared-code diff. A
clean-room CI checkout has one branch, so it cannot produce a sibling.

`build-scripts/ci/build_one.sh` refuses a sibling model outright rather than
building something that merely resembles one. Extending CI to the siblings means
first publishing each model's identity overlay (its `target.mak` block,
`version.conf`, model-only blobs) and a port path that works from a single
branch. The per-model banner art is already vendored here in `build-assets/`.

## Expectations and limits

- **Runtime.** A hosted runner has 4 vCPUs; the maintainer's box has 14. Expect
  hours, not the ~25–30 minutes a local build takes. Each variant is its own job
  to stay inside the 6-hour per-job ceiling, which means each pays a full compile
  rather than sharing a warm tree the way the local two-variant flow does.
- **Disk is the main risk.** The Broadcom tree plus toolchains is large and
  hosted runners are tight. The workflow reclaims space aggressively and puts the
  build tree on whichever volume has more room. If a run dies on disk, that is
  the reason.
- **No releases.** The workflow never publishes. Artifacts are unsigned outputs
  of a pipeline that has not yet been validated against a local build; the
  published releases remain the authoritative images.
- **Flashing is at your own risk.** This is third-party firmware for hardware you
  own. Read the install and rollback notes before flashing anything.

## Pins

| Input | Value |
|---|---|
| Upstream base | `RMerl/asuswrt-merlin.ng` tag `3006.102.8-beta2`, commit `a7ebfa133ad7e5efc23ed6bb8ee912bc72fd00b3` |
| Toolchains | `RMerl/am-toolchains` commit `d1af80e6b6686a4edc680386c09a8361453dd5c1` (crosstools gcc-10.3) |
| Build OS | Ubuntu 20.04 container, non-root user `reaper` (uid 1001) |

The base pin never moves. Upstream carry-forwards are cherry-picked into the
patch series rather than rebased, so this reproduction recipe stays stable across
releases.
